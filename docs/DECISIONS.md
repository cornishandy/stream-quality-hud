# Design decisions

## 1.13.0: measure the video that is actually playing
25 Oct 2026. Andy asked for a physical reading of the video on screen, not a calculation from a standards table: peak, range, box and bar figures, and the running average in the pill. Estimated listed bitrates stay useful. Actual encoded video is better when the pieces can be read exactly.

> also, I kind of want an actual analysis of the video I'm watching, not logical calculations and not based on standards, but actual "physical" analysis of the video I'm watching, and then give me peak, range, and then all the box and bar type analytics, and display running avg. in pill title. estimated values are useful, but if we can get actual values it would be MUCH BETTER!

GPT-6-Astra's pre-OK and GPT-6.1-Sol's challenge were both NO-GO on the first plan. Plan r2 folded those findings in. Astra's 9:20 PM recheck (Addendum A) overrides r2 where they differ. Each finding below is met in the build.

- **Presentation time, not decode time** (Sol). A decode-time peak on the reference file was 0.637% off the movie's presentation-time peak. The reader keeps integer ticks, reads `trex` defaults, signed composition offsets and the simple edit list, and the tests compare one-second presentation bins with ffprobe.
- **An append is not the same as accepted samples** (Sol). Sequence mode is unavailable. Samples outside the append window, and samples before the next keyframe after an abort or a trim, are dropped. Astra's recheck: a fragment is emitted only after `updateend` with no error, and only once each sample's own bytes have arrived. An empty `mdat` before the real one releases nothing. A sample is kept only when its whole interval sits inside the append window.
- **Watched time is not the latest fragment in a second** (Sol). Removing buffered media while paused does not rewrite seconds already watched. The ledger is a merged union of watched intervals. Overlapping samples contribute only the unseen part. Four quarter-second commits in one second match one whole-second commit.
- **A hidden player is not the one on screen** (Sol). The reader answers only for the element that was asked. A worker-owned handle stays unavailable. There is no "most recent MediaSource" guess, so a hidden decoy cannot supply the numbers.
- **Do not invent a second request** (Sol, and Astra). Chrome and Orion install the reader as a page-world content script, which does not send a CSP report. There is no blob fallback. Safari's inline script is limited to the service list Andy chose at about 9:05 PM ("Checked services"), knowing a site that tightens its rules could receive a report. Safari may send a site a CSP violation report the first time, if that site has started blocking inline scripts; the HUD then never tries there again. A policy that allows inline scripts, including a report-only policy that allows them, sends none. If a report-only policy blocks the script but the reader still ran, this page is measured.
- **Replay must not double count** (Sol). Each session keeps the highest sequence number. A second ping does not add the same pieces again. A gap after the first accepted record stops measurement rather than leaving a hole.
- **Caps stop the measurement** (Astra's recheck, over the earlier "drop the oldest and show a gap"). Sample count and fragment size are checked before the work. The watched ledger stops at 6 hours, pinned inits at 16 sources, the transport queue at 600 records or 3 MB, and the pending samples at 200,000. At any cap the panel says `Measurement stopped at its safety limit.` It does not show an approximation. Parse, accounting and render times are reported as p95. The Safari block list is the userscript's GM storage, not the page's localStorage.
- **Several video tracks** (Astra). More than one video track on the owned MediaSource is unavailable. A representation switch replaces that SourceBuffer's init, so a normal quality change is not treated as two tracks. Two tracks in one init, or two buffers each with a video track, stays unavailable.
- **Frame size at commit** (Astra). The size is the playing element's `videoWidth` by `videoHeight` when the second is committed, not the init box. That covers in-band size changes. Edit lists other than none, or one non-empty edit at rate 1, are unavailable.

Grades use the measured average only after 120 seconds of the current size and codec, with at least 90% of that configuration's own watched interval committed. Until then the listed bitrate grade stays. The pill keeps today's listed rate until 5 seconds are committed and coverage is at least 90%, then it shows the average. Unavailable cases name the reason and show no bitrate. A ready measurement with no complete second shows the average and says the highest second and range need a full measured second.

## 1.12.0: the pill keeps the size, and drops the words that never change
25 Oct 2026. Andy said every film was reading SDR, and BlackHole (the virtual audio device he uses) forces 2-channel stereo, so those pill words told him nothing. The size stays.

- **The pill reads size, video codec and listed bitrate**, such as `720p · H.264 · 3.0 Mbps`. A range stays a range. An HLS figure that includes sound says so. A codec is left off when the list names more than one.
- **SDR and channel layout stay in the open panel.** HDR is added on the pill only when this picture is actually HDR. The amber dot still marks a problem.

## 1.11.0: the corner pill names the picture and the sound
25 Oct 2026. Andy asked the top-right pill to stop listing problems, and to show key video and audio info. He picked picture and sound (`720p SDR · Stereo`). GPT-6-Astra preferred size and colour only. Gemini 4 Argon preferred picture and sound when the pill should carry audio. Both kept the amber dot as the pill’s only problem mark.

- **The pill uses the panel’s own words.** Size and colour stay as they already read (`720p SDR`, `1080p HDR10`). The sound word is the same one in the Sound block (`Stereo`, `Mono`, `5.1 surround`, `Dolby Atmos`, `No sound track`). When the browser does not report a track, the pill leaves sound off. It does not guess stereo.
- **Problems stay in the open panel.** Titles such as “Picture below 1080p” and “Dropping frames” are not the pill text. The dot still turns amber for those problems.
- **A newer film card on this Mac is kept.** The loopback box can fill in another browser’s card, but an older copy from the box does not replace a newer one already stored here.

## 1.10.0: compare browsers that actually played this film
25 Oct 2026. Andy asked for the cross-browser checker to be built into the extension, after Chrome and Safari were sent different Hulu ladders for the same film.

- **A card is saved only when this video’s own list is confirmed.** It records the best playable offer on that list (size, codec, listed bitrate, whether the figure includes sound, HDR, frame timing, and whether the page filters the picture). It does not record the low rung a player starts on, a playlist URL, a segment URL, or a cookie.
- **A recommendation needs a second observed card for the same film path.** The film id is the host plus the path, with the query stripped. One browser, or a published service cap, produces no “Watch in” line. Cards older than 7 days are dropped.
- **Order:** higher resolution, then HDR when this screen can show it, then codec-adjusted bits outside a 15% band, then even frame timing, then a picture the page does not filter. Surround does not break a tie. On a Mac the browser folds it, and the panel cannot see the speakers.
- **The line is one sentence.** The current browser wins with no switch link. Chrome, Edge and Firefox get an open link (`google-chrome://`, `microsoft-edge:`, `firefox://open-url`). Safari has no open-url scheme, so the row names Safari and the page address.
- **Where the cards meet:** this browser’s localStorage, and a loopback box at `127.0.0.1:9791` when `node tools/card-box.mjs` is running. Chrome’s service worker is the only thing allowed to contact that address. Safari’s userscript uses `GM_xmlhttpRequest` with `@connect 127.0.0.1`. If the box is down, the panel keeps this browser’s card and does not invent the other browser’s.

## 1.9.0: playback first
22 Oct 2026, Andy requested drastic consolidation, visible grades, plain sound explanations, new references, and Astra/Gemini judgment. Both independently chose the compact inspector over grade-first hero letters.

- **Hierarchy:** observed Picture → Data grades → observed Sound → supported issue → Technical details. No global “Nothing to change” conclusion from incomplete evidence. Service ceilings do not prove current-title eligibility, selectable sound, or an available upgrade.
- **Grades stay findable:** show both letters with complete ranges/up-to bounds, meanings and percentages. Without inputs, name the actual blocker once. Missing/ambiguous/unsupported codec and absent size references are distinct; a valid Disc grade survives a missing Streaming reference. Math is unchanged from 1.8.0.
- **Sound describes the stream:** stereo means two channels, left and right; AAC is its format. AAC alone is not stereo. Spatial audio is Netflix's title-dependent 2-channel mix, not a macOS switch. Service/device possibilities remain in Technical details.
- **Evidence determines emphasis:** only current video's matched ladder or observed problems enter the overview. A Chrome→Safari service-wide ceiling, low grade, or 60 Hz page callbacks alone do not justify an upgrade instruction. Decoder support alone never proves a selectable audio track.
- **HDR uncertainty remains uncertainty:** overview advice requires positive decoder support. An unreported codec does not mean the browser lacks it; the diagnostic fallback distinguishes `null` from `false` (Astra final gate caught this introduced branch error; targeted parser/capability cases now cover both engines).
- **No absent-row placeholders or locked heights:** remove stale blank rows and the mechanism that caused WebKit's 64px Details jump. Persistent disclosure and focus, scroll restored after rendering. Overflow scrolls instead of clipping the grades. Normal, unknown and irrelevant diagnostics leave the overview; observed technical facts remain one disclosure deep.
- **New design references inspected 22 Oct 2026:** [GOV.UK summary list](https://design-system.service.gov.uk/components/summary-list/default/index.html), rendered/screenshotted at 390px and 1280px: labels and values share clear edges, phone stacks values under labels. Borrow proximity, not full-page scale or edit links. [Apple disclosure controls](https://developer.apple.com/design/human-interface-guidelines/disclosure-controls), rendered/screenshotted at both widths: essential controls visible, related detail behind a named disclosure. Borrow one disclosure, not branding/illustrations. Gemini additionally checked Fast.com live desktop DOM (primary result above supporting diagnostics); screenshot and mobile behavior were unverified there. T3 preview snapshots timed out twice; lead verified the other references with the repository's Playwright browser tooling.
- **Tokens:** host system/Avenir typography, 22px current picture/grade, 13px body, 12px supporting labels. 352px panel with a common left edge, neutral nearly opaque overlay for reliable contrast. Colour indicates observed issues; no decorative grade badges. P1/P2/P3/P6/P7 from the shared principles library applied; overview scrolling is needed so small windows never clip essential facts.

# Decisions

Why the HUD works the way it does. Newest first.

## 1.8.0 (21 Oct 2026): streaming grade beside the disc grade
- **Two grades** (Andy: "add a grade for quality of that medium, so is this the best streaming quality video available?"; scope picked from examples: "Both, size first"). The **streaming grade** compares the encode's codec- and size-adjusted bits per pixel with a *high mainstream streaming reference at the same size*; the old data grade becomes the **disc grade** (against a 1080p Blu-ray). When the size is below 4K, the note adds "some films and shows stream in 4K".
- **References** (GPT-6.1-Sol's research, `~/Library/Caches/hud-streaming-grade/bitrates.md`), H.264-equivalent at 24 fps: 4K 46.4 Mbps (Apple TV+, 29 Mbps HEVC, measured report), 1080p 11.2 (Max, 6.99 Mbps HEVC, measured report), 720p 4.5 (Apple's HLS authoring target, a fallback, not a measured maximum). They are high references, not service ceilings. Other sizes read "reference unavailable". Per-size, because the size adjustment doesn't make them equal (0.166, 0.225, 0.33 adjusted).
- **Bands describe data, not picture quality** (GPT-6-Astra's pre-OK): A ≥ 80% of the reference "generous data", B ≥ 55% "solid", C ≥ 35% "moderate", D ≥ 20% "lean", F "very lean". Grades never change the Picture verdict, mark or steps.
- **Uncertainty always shows.** A range ("C or D", "up to C") when the exact version or sound share is unknown, even when both ends share a letter; an HLS list with only peak bitrates (no AVERAGE-BANDWIDTH) grades as "B or lower", "listed peak".
- **Short windows keep Details reachable** (GPT-6-Astra's final gate, round 1 NOT-OK): the closed panel is a flex column whose summary rows clip first, so the Details control stays visible down to a 400 px window. GPT-6.1-Sol's code review: APPROVE. Astra round 2: FINAL-OK. Known and older: in WebKit, a refresh pulls an open, scrolled-to-bottom Details up by about 65 px.
- **Scorecard keeps each grade's meaning and percent** (Andy, 21 Oct 2026: "can the hud include the percent and meaning, and also the letter grade and its meaning"), so Astra's shorter muted line ("Rough data grades.") was extended to carry them.

## 1.7.0 (21 Oct 2026): data grade, overlays, sound the player picks
- **Data grade** (Andy: the bitrate ranges said "Normal" without saying how good). Bits per pixel = video bitrate ÷ (width × height × frame rate), then adjusted for codec (H.264 1, HEVC/VP9/Dolby Vision 1.6, AV1/VVC 2) and size (fourth root of the area against 1080p). Bands: A ≥ 0.30 disc-like, B ≥ 0.15 generous, C ≥ 0.09 typical streaming, D ≥ 0.055 lean, F starved. A typical 1080p Blu-ray (H.264, about 30 Mbps at 24 fps) scores about 0.6, which gives the "% of a Blu-ray's data" figure. The factors and bands are a rough guide (Opus's judgement, not a measurement), and the panel says so. HLS figures cover the video plus its largest sound pairing (RFC 8216), so the largest listed sound bitrate is taken off when every sound track lists one; otherwise the grade allows up to 768 kbps of sound and can read as two letters ("D or F"). When several bitrates are listed at the playing size and the exact one isn't known (Safari playing a master list itself), the low end is graded too, so it reads "B to D" with "up to" on the figures (Claude Fable 5.1's final gate, round 1).
- **Overlays.** The HUD lists what the page draws over the video (shading, tints, solid layers, subtitles, controls, canvases, images) and any filter, opacity or blend applied to the video or the elements that hold it. Stacking is approximated by position and z-index under the shared ancestor, then page order; coverage uses the picture's own rectangle, not letterbox bars; darkness counts the opacity of the layers holding a shade, and light tints are called light. When nothing is found it says a player can hide layers from this check, since closed shadow roots and unusual colour spaces can't be read. GPT-6.1-Sol's review (round 1, NO-GO) found: layers behind the video, letterbox bars, opacity and light tints, missed pseudo-element and color() layers, the HLS sound share, a frame rate from the wrong version, and a sound line that blamed the player when the playing track was unknown. All are fixed. Its HLS harness expects an exact letter; the HUD gives a range instead when the list doesn't say the sound's bitrate. `elementsFromPoint` isn't used because it skips `pointer-events: none` layers, which is how most shades are drawn. A filter or a solid layer is Unusual; a shade of 25% or darker is a Note.
- **Chrome looking darker than Safari is not a layer.** An earlier answer said Chrome "adds a layer". GPT-6.1-Sol's research (21 Oct 2026) rejected that: both browsers sometimes hand video to a Core Animation layer and sometimes convert it themselves. The likelier cause is the colour conversion: Chromium's source notes that "Apple's CoreVideo uses gamma=1.961", while Chromium's ordinary BT.709 conversion uses "the same transfer function as sRGB". A page can't see which path runs, so the panel lists it under "Can't tell".
- **Lines don't bounce** (Andy: rows appearing and disappearing made the open panel jump). While the panel shows one video, a line once shown keeps its place (reading "—" when it has nothing now), each line keeps the tallest it has been, and the panel never shrinks by itself. So a line can push the others down once, the first time it appears, and nothing moves after that. A new video, closing the panel, or opening or closing Details starts afresh (Claude Fable 5.1, final gate round 2, found the panel kept its old height on a new video; fixed). "Over the video" always shows, reading "nothing found" when empty.
- **The player picks the sound track.** A better track in the stream list used to be ▲ with "Pick … in the player's audio menu". Web players' audio menus pick the language, not the format (Peacock's is "Audio & Subtitle"), and Dolby's own guidance says a provider "may choose to only deliver the Atmos experience to capable devices". So it is now – with "<service>'s player chose it over <track>", and no step. Chrome on a Mac can't decode E-AC-3 at all (Chromium builds the AC-3/E-AC-3 decoder for Cast and tvOS, not Mac); Safari can, including Atmos (JOC).

## 1.6.0 (19–20 Oct 2026): compact scorecard
- **F2 Compact scorecard**, chosen by Andy from 5 mockups and 2 finalists judged by GPT-6.1-Sol, GPT-6-Astra, Grok 4.7 and Gemini 4 Argon.
- **Five marks:** ▲ better on this Mac, ◇ worth trying, – top sent, ✓ computer best, ? unknown. Shape and colour together; the row text carries the words.
- **Pill rules:** shown for a known service, or a video of 10 minutes or more; fades after 3 seconds of idle while the video plays.
- **Accuracy rules:** no "pixel for pixel", no "TV apps only", and the 60 Hz line names a Safari setting worth trying rather than a claim that the Mac holds the video back.
- **Round 1 corrections:** timing runs only while the pill or panel is connected; cold Smoothness reads “measuring…” without a judgement. Unestablished limits read “unknown”, not a claim that the service publishes nothing. Prime Video’s unnumbered HD needs 1080p for ✓; mono ranks below stereo. Details names the stream list and the browser receiving it.
- **Final gate (Claude Fable 5.1):** the unnumbered-HD rule applies only when no stream list says more, so a 720p film whose Prime Video list goes to 1080p is still flagged; a mouse click leaves the pill unfocused, so it can fade and Space still reaches the player.

## 1.5.1 (19 Oct 2026): shorter wording
- **Headings are 2 to 5 words, under 36 characters,** with the words that matter first and no filler: "Best for Safari", "Picture below best". Notes and lines get the same treatment. The panel had grown wordy enough to lose its meaning.
- **"Elsewhere", not "Better".** The service's best anywhere (say, 4K HDR in its TV apps) read as if this film was on offer in 4K. The line now starts "Elsewhere:" and ends "not every title".
- **Refresh says whose limit it is.** "Safari's page limit, not the video's" replaces "draws pages at 60 Hz to save power", which read as the Mac holding playback back.

## 1.5 (18 Oct 2026): judged rows and a verdict, not raw numbers
- **A verdict headline replaces the green status text.** The old line ("Best size…") coloured a technical fact green, which didn't answer the real question: is this the best I can get here, and if not, where? The verdict now says that in words, worst problem first: not the best picture yet → best picture but not the best sound → best this browser gets, more elsewhere → best this site offers → can't confirm.
- **A cue dot carries the colour, not the text.** It sits in the top-right corner, where a projectionist's reel-change mark appears. Sage means best here, blue means more exists elsewhere, amber means not the best, and a hollow ring means can't confirm.
- **Every row is judged Normal, Unusual or Note, with a reason.** Only exceptions get colour (amber for Unusual), so a normal stream reads calm.
- **Sound got its own section:** the playing track (WebKit's track configuration, or the downloaded audio matched to the list), the list's best track and whether this browser says it can decode it, and each service's published sound limits.
- **"After this" row:** the HUD sits before any audio processing on the Mac, so it says what comes next (Movie Sound, a Chrome audio extension) and that it can't see it.
- **Refresh vs smoothness.** Safari draws web pages at about 60 Hz even on a 120 Hz screen (the video itself is drawn natively), while Chrome reports the screen's real rate. So "Refresh" is a note, and "Smoothness" is measured from `requestVideoFrameCallback` frame times (even or uneven pacing). WebKit reports when frames are due, not when they were shown, so there the HUD says "can't check here" rather than guess.

## 1.3–1.4: Safari, published caps, refresh rate
- **Safari runs it as a userscript** through the free Userscripts app. A real Safari extension needs Xcode and a signing identity, and a temporary developer extension disappears when Safari quits. `hud.js` already works without extension APIs, so the userscript is the same file with a header.
- **Published caps per service** (Netflix, Prime Video, Disney+, Hulu, Max, Apple TV+, Paramount+, Peacock, AMC+, MUBI, Criterion Channel), taken from each service's own help pages, with the source and quote for each in `SERVICES.md` and `SOUND.md`. Where a service publishes no browser cap, the HUD says so instead of inventing one.
- **Orion** (a WebKit browser that presents Chrome's user agent to extensions) is detected by WebKit-only APIs and named as Orion, with no service caps, since no service publishes one for it.

## 1.0–1.2: exact evidence only
Two independent code reviews (GPT-6.1-Sol, NO-GO twice) shaped these rules:
- **No background requests, no host permissions.** An early version fetched stream lists again from the extension's background, with access to every site. That's a privacy and security risk, so it was removed. Now the HUD only re-reads lists the page itself already downloaded, from inside the page with the page's own rights (usually from the browser's cache).
- **A verdict needs the video's own list.** That's either its HLS source, or the list whose segments match the video's newest downloads since it started playing. A trailer's list, a hidden second video, trick-play tracks or a multi-period DASH list can't certify "best".
- **The HUD never touches audio.** It creates no AudioContext and doesn't read channel counts through Web Audio, so turning it on or off can't change what you hear.
- **Toggle is Control+Shift+H.** Control+Option+Shift combinations are commonly taken by window managers.
- **A bare `<video>` in full screen can't show the panel.** Nothing can draw over it. Sites that put their whole player in full screen (most do) are fine.
